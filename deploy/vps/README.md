# Shade VPS: состояние и эксплуатация

Проверено 15.11.2026. Адрес: https://13-143-207-108.sslip.io.
Debian 13, Node.js 22 LTS, Caddy, systemd. Node слушает только 127.0.0.1:3000.

## Файлы на сервере

- `/opt/shade/current` — ссылка на активный релиз; предыдущие релизы сохраняются.
- `/var/lib/shade/data` — постоянное зашифрованное хранилище, включая аватарки в `stickers.json`.
- `/etc/shade/shade.env` — закрытая конфигурация. Не копировать в Git и отчёты.
- `/var/backups/shade` — резервные копии, включая ключевые данные для расшифровки.
- `/var/log/shade-vps-tests.log` — результаты изолированных серверных тестов.
- `/etc/ssh/sshd_config.d/60-shade-hardening.conf` — вход по ключу, парольный вход отключён.

Существующие данные перенесены с сохранением session secret и ключа сервера.
Firebase service account не был доступен: push-уведомления отключены.
SSH работает по уже существующему ключу владельца. Перед применением hardening на
другом сервере сначала проверить вход по ключу в отдельном SSH-сеансе.

## Обновление

`bootstrap.sh` не запускать повторно без аудита: он содержит полное обновление ОС.
Для текущего сервера достаточно подготовить архив серверных JS и package/lock файлов,
загрузить его и файлы `deploy/vps` в закрытый upload-каталог и запустить:

```sh
bash /root/shade-upload/deploy.sh /root/shade-upload
```

Не включать `.env`, сертификаты, логи и локальные тестовые базы в архив исходников.
Импорт `upload/data` выполняется только в пустое хранилище. При обновлении существующие
данные сохраняются. Кандидат сначала проверяется на отдельной копии данных и loopback-порту.
Затем переключается systemd, проверяется health и применяется проверенный Caddyfile.
Автоматического удаления релизов и пользовательских данных нет.
При откате кода не подменять текущие данные старой базой: это потеряет новые сообщения.

Резервная копия запускается ежедневно в 03:17 по часовому поясу VPS, проверка здоровья —
каждые 2 минуты. Копии находятся на этом же SSD: требуется отдельно согласовать внешний
backup и срок хранения. Автоматическая очистка резервных копий не настроена.

Проверки:

```sh
systemctl status shade caddy
journalctl -u shade --since '10 minutes ago'
/usr/local/sbin/shade-backup
```

Публичная проверка с рабочей машины (нужны dev-зависимости server):

```sh
node server/tools/production-smoke.js https://13-143-207-108.sslip.io
```

Она проверяет доверенный HTTPS, серверный ключ (при заданном ожидаемом fingerprint),
закрытость аватара и admin API, настоящий WSS upgrade и отказ неверной сессии.
Обмен сообщениями между тремя клиентами проверен отдельно на VPS с тестовым хранилищем;
это не проверка переписки двух физических телефонов через публичный proxy.
Caddy удаляет X-Session-Token и X-Username из новых access-логов.

## Android

Из `client`:

```sh
flutter build apk --release --target-platform android-arm64 --dart-define-from-file=config/production.json
```

`production.json` уже содержал адрес VPS, Google Web Client ID и верный fingerprint
серверного ключа. Файл игнорируется Git. TLS-проверка остаётся включённой.
Release APK подписан настроенным release-ключом. На Galaxy A31 была debug-сборка с другой
подписью, поэтому release-обновление Android отклонил. Удаление приложения не выполнялось.
Для реальных проверок установлен debug APK из тех же исходников с production-конфигурацией.
Переход с debug на release требует отдельного безопасного плана переноса данных/ключей.

## Будущие звонки 1 на 1

WebRTC в текущем клиенте и signaling для звонков ещё не реализованы.
Рекомендуемый вариант: `flutter_webrtc`, существующий авторизованный Socket.IO для
invite/accept/reject/end, SDP offer/answer и ICE candidates; медиа напрямую между peer.
Каждый callId привязан сервером к двум участникам. Сервер сам определяет отправителя,
проверяет участника, занятость, таймаут звонка, размеры SDP/ICE и частоту событий.
Не логировать SDP, ICE и TURN credentials; закрывать tracks, соединение и подписки
при завершении/потере сеанса. Потребуются разрешения микрофона/камеры и проверка Android lifecycle.

STUN помогает обнаруживать внешний адрес, но не гарантирует связь через мобильные NAT.
Для надёжной работы нужен TURN с краткоживущими credentials. Предпочтительно отдельный
TURN-сервис; coturn на этом VPS возможен после проверки пропускной способности и квот.
Медиасервер/SFU и TURN сейчас не устанавливались. Групповые звонки не входят в эту схему.

Источники: [WebRTC peer connections](https://webrtc.org/getting-started/peer-connections),
[TURN](https://webrtc.org/getting-started/turn-server),
[Caddy WebSocket proxy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy),
[Caddy log filtering](https://caddyserver.com/docs/caddyfile/directives/log).
