# Мультиустройство Shade: архитектура синхронизации, threat model, статус

Ветка `glm-multidevice` (база `v2-pwa-integration` 9a94fb0). Документ фиксирует
фактическое состояние device-v2, добавленный в этой ветке pairing-флоу второго
устройства (только клиентская часть, без изменения протокола) и то, что
требует отдельного согласования (recovery-сессия, перенос истории).

## 1. Как синхронизация устроена сегодня (без изменений в этой ветке)

- Каждое устройство — пара RSA-4096 (OAEP-SHA256 + PSS-SHA256), ID = SHA256 от
  обеих публичных SPKI. Ростер устройств — подписанный каталог (manifest chain),
  корень — genesis, подписанный первым устройством; lease ≤ 24 ч.
- Каждое сообщение шифруется отдельным AES-256-GCM ключом и рассылается
  конвертами **всем устройствам обоих участников** (fanout), включая устройства
  отправителя. Сервер хранит per-device очередь (≤200 сообщений / 8 МиБ) до ACK.
- Чтение/ACK/socket — per-device подписанные операции (device proof на каждый
  запрос + Google/legacy/device-сессия). Отзыв устройства чистит его очередь,
  push-подписку и запрещает повторное использование ID/ключей.
- Поэтому «получать новые сообщения на обоих устройствах» после добавления
  устройства работает без каких-либо новых серверных механизмов: fanout сам
  доставляет конверт на каждое устройство ростера.

## 2. Чего не хватало: подключение второго устройства

Сервер (`registry.install`) уже принимал: подписанный доверенным устройством
manifest + **свежий pairing proof нового устройства** (подпись нового устройства
над `pairingText`, срок ≤ 5 мин). Не существовало только клиентского пути:
на новом устройстве после Google-входа был тупик «Нужна привязка устройства…
добавление устройства через интерфейс ещё недоступны».

### Добавленный flow (шаги пользователя)

Транспорт offer/confirmation — вне канала сервера (clipboard, текстовые блоки).
Каждый блок — самодостаточный, версия в префиксе.

1. **Доверенное устройство** → Настройки → «Добавить устройство»: генерируется
   одноразовый **challenge-код** (120 бит, Crockford-base32, 4 группы по 6,
   в памяти клиента, TTL 5 мин) с предупреждением «только для вашего устройства».
2. **Новое устройство** → вход через Google → «Подключить это устройство»:
   ввод challenge-кода → создание локального ключей-хранилища (vault, RSA-4096,
   своя фраза устройства ≥16, ключи durable в IndexedDB до approval) →
   генерация **offer** (`shade-pair-v1:<base64url JSON>`): аккаунт, дескриптор
   (обе публичные SPKI + ID), echo challenge, pairing-nonce, срок 4 мин,
   подпись PSS над `pairingText` (ровно та, что потом проверяет сервер).
3. **Доверенное устройство**: вставка offer → проверка (аккаунт совпадает,
   challenge echo совпадает и не истёк, подпись новго устройства валидна,
   ключи RSA-4096, ID = SHA256(ключи)) → экран подтверждения с отпечатком
   устройства и именем аккаунта → «Подтвердить»: manifest revision+1 со всем
   ростером подписывается ключом доверенного устройства, `install` с proofs
   → **confirmation** (`shade-pair-confirm-v1:<base64url JSON>`):
   genesis + последний manifest (подсказка; доверие строится ниже).
4. **Новое устройство**: вставка confirmation → проверка genesis →
   **device-session bootstrap** (`/api/v2/challenge` без сессии для op
   `device-session` → proof → `/api/v2/session/device`) → сразу после этого
   устройство само получает **полный каталог** op'ом `directory` и проверяет
   его целиком (`verifyHistory`) против pinned genesis — окончательный
   checkpoint строится по серверной цепочке, а не по clipboard-подсказке →
   сохранение начального состояния → обычный `start()`/sync. Готово.

Ключевое свойство: confirmation — только «маршрутный указатель». Состояние
(`own`) нового устройства строится из **полного каталога, полученного и
проверенного после вступления в ростер**, поэтому clipboard-канал не является
доверенным для целостности цепочки (см. threat model).

### Почему challenge-код до offer

Offer подписан самим новым устройством и **не привязан** к аккаунту кроме
поля `account`: злоумышленник может изготовить валидный offer с чужим именем
аккаунта. Без challenge фишинг «вставь этот код — добавишь устройство» добавил
бы устройство атакующего в ростер жертвы при слепом подтверждении. Echo
свежего (≤5 мин) challenge-кода, показанного только на экране доверенного
устройства, разрывает эту цепочку: поддельный offer не знает актуальный код.
Финальная защита — осознанное подтверждение с отпечатком на доверенном экране.

## 4. Threat model (pairing и мультиустройство)

Активы: приватные ключи устройств, plaintext переписки, членство в ростере.

| Угроза | Оценка | Защита |
| --- | --- | --- |
| Google-аккаунт скомпрометирован | Критично рассматривать | Google подтверждает только личность, не ключи: войти на новом устройстве без approval доверенного устройства нельзя (`update()` требует pairing proof + подпись из предыдущего ростера). Сессия сама по себе не читает очереди (device proof на каждый op) |
| Фишинг offer («вставьте код») | Высокий без challenge | Echo свежего challenge-кода с доверенного экрана (≤5 мин) + явный экран подтверждения с отпечатком; offer с чужим аккаунтом отклоняется по challenge |
| MITM в clipboard-канале offer | Средний | Offer проверяется подписью нового устройства; подмена ключей ломает подпись; подмена аккаунта ломает challenge echo |
| MITM в clipboard-канале confirmation | Низкий (DoS) | Confirmation не является доверенным: устройство после вступления само качает полный каталог и проверяет цепочку; подмена видна как другой аккаунт/ошибка |
| Replay offer/челленджа | Средний | Pairing proof живёт ≤4 мин (сервер ≤5 мин), challenge ≤5 мин, манифест CAS по revision; повторный install того же манифеста → `Stale` |
| Rollback/fork каталога | Средний | Цепочка revision+previous+подписи; клиентский checkpoint (`verifyHistory` с checkpoint) отвергает откат |
| Кража доверенного устройства | Высокий | Vault зашифрован фразой (600k PBKDF2), ключи non-extractable; украденное устройство с разблокированным экраном может одобрить чужое — как в Signal/WhatsApp; отзыв устройства из другого ростера |
| Утечка через сервер | Средний | Сервер видит только метаданные и ciphertext; offer/confirmation через сервер не проходят; приватные ключи никогда не покидают устройство |
| Отзыв устройства в момент офлайн-отправки | Низкий | fetch фильтрует сообщения от отозванных отправителей; недоставленные копии отозванного устройства удаляются при install |
| Потеря нового устройства до approval | Низкий | Ключи durable в IndexedDB, offer можно перегенерировать (новый proof, те же ключи); никаких серверных следов до install |
| Ограничение lease 24 ч | Известное | Автопродление при `refreshOwn` (<1 ч до конца); злой сервер может скрывать более новый отзыв до конца lease — известное ограничение кандидата (MULTIDEVICE_V2 §5) |
| Подделка genesis при первом контакте (TOFU) | Низкий | Genesis самоподписан корнем; на новом устройстве видны аккаунт и отпечаток genesis; подтверждение осознанное |

Явно вне модели: XSS/подменённый JS на origin (MULTIDEVICE_V2 §8), физический
доступ к разблокированному устройству, компрометация сервера целиком (он не
получает ключей, но может задерживать доставку — честно отражается в UI).

## 5. Требует согласования с Qwen (не реализовано в этой ветке)

### 5.1 Recovery-сессия (приоритет 4)

Проблема: устройство с валидным recovery-ключом не может получить текущий
каталог (`directory` op требует активный device proof) — построить manifest
revision+1 не из чего. План:
- `POST /api/v2/session/recovery`: challenge → подпись recovery-ключом (ключ
  проверяется по `genesis.recoveryKey`; genesis клиент приносит в запросе —
  сервер сверяет `genesisDigest` с хранимым) → короткоживущая сессия
  `kind:'recovery'`, разрешающая ТОЛЬКО `directory` и `install`.
- Клиент: unlock recovery-пакета → fresh vault → manifest со всеми текущими
  устройствами минус потерянные (или пустым ростером, если все потеряны:
  fresh device + signer 'recovery') → install → обычная работа.
- Совместимость: изменения аддитивны (новый маршрут + новый signer-кейс),
  C1–C7 и `install` не меняются. Recovery-ключ в genesis уже существует.

### 5.2 Перенос истории (приоритет 3)

Нельзя через существующий `send`: receipts-лимит 10000 глобален и не
чистится — перенос даже средней истории исчерпает ёмкость аккаунта навсегда
(проверено: `registry.receipts` нигде не пrunится). План:
- Новый op `history.transfer` (device proof, авторизация=участник): доверенное
  устройство кладёт в per-device staging нового устройства пакеты ≤64 КиБ
  (payload = E2EE-записи, зашифрованные OAEP-ключом нового устройства, с
  оригинальными метаданными), **без** учёта в receipts/очереди сообщений.
- Курсор + идемпотентность по id пакета; лимиты: ≤N пакетов на аккаунт,
  общий объём-потолок, прогресс в UI.
- Альтернатива без сервера (хуже): self-chat поток — упирается в те же
  receipts/queue лимиты, отклонено.
- Threat model: история не должна проходить через сервер в plaintext —
  пакеты шифруются ключом нового устройства; replay отсекается курсором.

### 5.3 Прочее (уже известные блокеры)
- Expose `ALPHA_VAPID_PUBLIC_KEY` в `/api/session` (Web Push, C6).
- Очистка/лимиты receipts для долгой эксплуатации.
- QR-транспорт для challenge/offer (нужен bundled QR-энкодер или короткий
  staging-маршрут — отдельное решение).

## 6. Android ↔ PWA совместимость

- Протокол и форматы не изменились: Android v2 клиент (transport/repository)
  совместим с этой веткой без пересборки контрактов; golden-векторы не
  затронуты.
- Pairing offer/confirmation — платформо-нейтральный JSON; для Android-роли
  «новое устройство» нужен Dart-клиент pairing (vault уже есть в Android v2);
  для роли «доверенное устройство» — approve-экран. Криптопримитивы уже
  проверены межстеково (`device_crypto_interop_test.dart`, alpha-native interop).
- PWA↔PWA (два браузера/два профиля) — полный flow работает в этой ветке.

## 7. Инструкция интеграции

- Файлы этой ветки: `client/web/pairing.mjs` (новый), `alpha-client.mjs`
  (аддитивно), `alpha-ui.mjs` (аддитивно: pairing-экраны, 2 action-кейса,
  замена тупика boot на кнопку подключения), `alpha_app.dart` (1 тайл),
  `server/test/pairing.test.mjs` (новый), `client/test/web_alpha_pairing_test.dart` (новый).
- Конфликты маловероятны: файлы OAuth Qwen (`/auth/google`, handoff) и
  PRF-файлы GLM №1 (`device_binding.mjs`, `recovery-words.mjs`) не менялись;
  единственная точка касания — `alpha-ui.mjs boot()` (ветка «Нужна привязка
  устройства») и `alpha_app.dart` (карточка устройств) — маленькие, изолированные правки.
- Миграции данных нет: snapshot-формат и IndexedDB-схемы не меняются.
- Сервер не менялся вообще: деплой этой ветки требует только пересборки
  клиентской оболочки (`python client/tools/build_web_alpha.py`).
