# Матрица паритета Android ↔ Web Alpha (PWA)

Обновлена 16.11.2026, ветка `zcode/pwa-parity`. Источник — реальный код:
`client/lib` (Android, entrypoint `main_native.dart`) и `client/lib/main_alpha.dart`
+ `client/lib/features/web/` + `client/web/*.mjs` (Web Alpha).

## Архитектура Web Alpha

- Ключи, WebCrypto-шифрование, зашифрованный IndexedDB, очередь и транспорт
  device-v2 живут в JS (`client/web/`). Flutter (`main_alpha.dart`) — только
  проекция интерфейса: snapshot через `shadeReceive`, действия через `shadeAction`.
  Flutter никогда не получает vault'ы, ключи, backup или токены.
- Переиспользуемые Android-виджеты: `MessageBubble`, `MessageInput`, `AvatarView`,
  `buildShadeTheme()`, `ShadeLogo`, `ShadeMotion`, `ShadeEmptyState`,
  `ShadeDateSeparator`, `ShadeMessageArrival`.
- Auth (Google OAuth server-side + PKCE, разблокировка vault'а фразой,
  регистрация RSA-4096) — DOM-экраны `alpha-ui.mjs` до запуска Flutter.

## Приоритеты переноса (по пользовательской ценности)

- **P0 (сейчас):** reply, удаление у себя, профиль собеседника — реализуемо
  на клиенте без изменения протокола и сервера.
- **P1 (после контрактов):** typing/presence (C2), read-ACK (C5),
  «Избранное» (C1), displayName/аватары (C7).
- **P2 (крупные):** фото в чате (C4), удаление у всех (C3), Web Push (C6),
  пагинация/snapshot-лимит, стикеры.

## Контракты интеграции device-v2 (требования к backend/протоколу)

Изменения протокола и сервера в этой ветке **не выполнялись** — только точные
требования. Файлы-цели: `client/web/protocol/device-v2.mjs`,
`server/multidevice/registry.mjs`, `server/alpha.mjs`.

### C1 — «Избранное» (self-чат)
`messageText()` в `device-v2.mjs:180` требует `m.from !== m.to`; `verifyMessage()`
строит ожидаемый fanout из `[sender, recipient]` и задвоит конверты при
совпадении аккаунтов. Нужен согласованный вариант: либо разрешить `from === to`
с дедупликацией конвертов (sender-рейс = recipient-рейс), либо серверный
self-notify op. Криптография при self-send не ослабляется: конверты шифруются
ключами своих устройств, подпись и проверки истории неизменны.

### C2 — Typing / presence
Socket.IO в alpha-сервере — только wake-up подсказки (`inbox`/`receipts`).
Требуются отдельные события присутствия с авторизацией той же схемой
(auth + подписанный proof при handshake), без содержимого сообщений:
`typing {account, peer, until}`, `presence {account, online}`. Хранить состояние
только в памяти процесса; доставка — в room собеседника. Отсутствие подписи на
каждом typing-событии допустимо (это не состояние E2EE), но авторизация
handshake обязательна.

### C3 — Удаление у всех
v1-сервер имеет операцию удаления; в device-v2 её нет. Требуется op
`retract {refs[]}` с проверкой авторства каждого ref, удалением из очередей
получателей и каскадным `receipts`-уведомлением. Клиенты обрабатывают tombstone
`{ref, deletedAt}` и скрывают сообщение. Скрытие уже полученных расшифрованных
сообщений локально не гарантируется (история E2EE хранится на устройствах) —
в UI честно отображать «отозвано отправителем».

### C4 — Фото
Payload `encryptLegacy` допускает 64 КиБ на конверт (AES-256-GCM, RSA-OAEP
только для ключа). Фото 1280px/80% ≈ 200–500 КБ → требуется либо чанкование
на несколько подписанных сообщений с клиентской сборкой, либо расширение
лимита `express.json`/`maxHttpBufferSize` и схемы message v2.1 с
`media {mime, chunks}`. EXIF/ICC должен срезаться на клиенте до шифрования
(на web — через Canvas/ImageDecoder, аналог `prepareMessageImage`).

### C5 — Read-ACK
Локальный `readUntil` не создаёт сетевого подтверждения. Требуется op
`read {refs[]}` (или per-ref receipt kind) с той же подписанной авторизацией,
что и ACK доставки, и проекцией статуса «Прочитано» отправителю.

### C6 — Web Push
VAPID + service worker push; сервер хранит per-device endpoint (в manifest
устройства или отдельной записи registry). Уведомление — wake-up без
содержимого (тело всегда расшифровывается на устройстве после
разблокировки/хранения session-ключей — требует решения по фоновому
фetch/расшифровке или честного «Новое сообщение» без текста).

### C7 — displayName / аватары в v2
Alpha API сознательно не отдаёт displayName/фото (`docs/WEB_ALPHA_0_1.md`).
Требуется решение: либо включить публичные profile-поля в directory manifest
(подписанные, версионируемые, с revocation), либо отдельный op `profile` с
проверкой авторства. Аватары — бинарные blob'ы с revision-конфликтами
(аналог `avatar_repository.dart` Android).

## Ограничения текущей реализации

- Reply-схема payload'а — клиентское соглашение Alpha (`{"shade":1,"t","r"}`);
  server и подписи рассматривают payload как opaque. Будущий Android device-v2
  клиент должен принять эту же схему (контракт для C-интеграций).
- «Удалить у себя» — локальное скрытие на устройстве; другие устройства
  собеседника и параллельные вкладки сохраняют сообщение (как на Android).
- Старые сообщения без reply-метаданных отображаются как обычный текст
  (обратная совместимость).

  отдельной проверки), восстановление прокрутки на reverse-списке,
  320–1440 px, клавиатура, pageErrors = [].
- Настоящий Google OAuth / физический iPhone / standalone PWA / Android v2
  APK остаются непроверенными.
