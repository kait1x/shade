# Shade: перенос пользовательских данных v1 → v2

Что именно сохраняется, каким механизмом и что делать в нештатных случаях.
Техническая архитектура — `docs/V1_TO_V2_MIGRATION.md`.

## 1. Таблица переноса по сущностям

| Данные | Где в v1 | Механизм переноса | Результат |
|---|---|---|---|
| Аккаунт / постоянный ID | `users.json` ключ = username | `prepare` импортирует username + RSA-якорь (`root`) в v2-реестр; genesis подписывается исходным RSA на устройстве | тот же username, тот же ключ; дубликаты невозможны (root сверяется, genesis неизменяем) |
| Имя пользователя / профиль | `users.json.displayName`, `stickers.json.displayName` | копируется в snapshot `stickers` при prepare и обновляется при finalize | сохраняется |
| Аватар | `stickers.json.avatarImage` (приватный, не публичный URL) | копируется; `avatarOwner` пересчитывается как SHA256(v2-root) — тот же неизменный ключ, иная кодировка | сохраняется, доступ только участникам |
| Рамки аватара | `stickers.json.avatarFrame` | копируется | сохраняется |
| Подарки/стикеры, стена | `stickers.json.inventory/wall/receipts` | копируются | сохраняются |
| Контакты / связи | клиентский SQLCipher (`contacts`, `conversations`) + серверные публичные ключи | локальная БД не трогается; в v2 контакт подтверждается сверкой genesis digest по независимому каналу | локальные контакты сохраняются; доверие v2 требует явной сверки (модель безопасности, не потеря данных) |
| Личные чаты | клиентский SQLCipher | БД сохраняется при обновлении приложения | сохраняются |
| Групповые чаты | в v1 production отключены (`groupMessage` → отказ) | — | переносить нечего |
| История сообщений | клиентский SQLCipher (постоянная); сервер — offline-очередь TTL 7 дней | локальная история остаётся; недошедшая серверная очередь переносится one-way мостом `legacyInbox` | история доступна тем же ключом; порядок и исходные v1 ID сохраняются в мосте (`v1:<from>:<id>`) |
| Фото / файлы / вложения | v1: ciphertext `IMG:<base64>` в очереди/БД; аватары в `stickers.json` | мост переносит ciphertext без изменений; клиент декодирует `IMG:` в изображение; локальные вложения в БД не трогаются | открываются тем же RSA |
| Состояние прочтения | клиентская БД (`is_read`); серверные receipts (TTL 7 дней) | локальные отметки сохраняются; серверные receipts v1 не переносятся (истекают, относятся к доставке v1) | локально сохраняется; v2 read-ACK строится заново для новых сообщений |
| Настройки приложения | SharedPreferences / secure storage | не изменяются миграцией | сохраняются |
| E2EE-ключи | приватный RSA в secure storage (Keystore) | **не передаются на сервер**; исходный RSA-4096 становится `primary`-устройством v2; RSA-2048 — явная rotation на новый RSA-4096 с аттестацией старого ключа (см. §3); новый recovery-ключ генерируется на устройстве и шифруется фразой | старые сообщения расшифровываются тем же ключом (rotation — сохранённым legacy-ключом); приватный ключ не покидает устройство |
| Привязанные устройства | v1: одно устройство на аккаунт (сессия) | после enrollment добавляются через штатный pairing (QR + подпись владения) | безопасно; старые сессии v1 не копируются |
| Сессии | session/refresh токены v1 | не переносятся: после enrollment v1 отвечает `upgrade_required`; вход в v2 — Google (если привязан) или legacy-key proof | осознанная повторная авторизация тем же аккаунтом |

## 2. Что сервер НЕ делает

- Не расшифровывает сообщения и вложения (только at-rest метаданные очереди).
- Не получает приватные ключи и recovery-фразы.
- Не перезаписывает `users.json`, `messaging.json`, `stickers.json`, токены.
- Не создаёт второй аккаунт для того же username/ключа.
- Не меняет genesis после коммита (неизменяемость проверяется сервером).

## 3. Сценарии восстановления

### Пользователь потерял устройство / данные сайта
- Есть recovery-пакет + фраза → восстановление членства: новые ключи устройства,
  новый каталог подписывается recovery-ключом, потерянные устройства отзываются.
  **Старая история без локальной копии не восстанавливается** (E2EE).
- Есть другое доверенное устройство → pairing нового устройства.
- Нет ни того, ни другого → восстановление невозможно (ни Google, ни сервер
  не восстанавливают ключи). Честное уведомление; аккаунт остаётся занятым
  прежним якорем.

### Сбой во время enrollment (убийство приложения, обрыв сети)
- Журнал `v2_enrollment_journal` (schema v10) хранит подписанные genesis/manifest
  и зашифрованный recovery-пакет **до** сетевого вызова.
- Повтор с той же фразой: сервер возвращает уже зафиксированный tip (resume)
  либо каталог перенимается через `/api/session`; recovery не теряется,
  второй genesis не создаётся.
- Неверная фраза: честная ошибка, журнал не повреждается, ключи не пересоздаются.

### Ошибка миграции одного аккаунта
- Статус `failed` + код ошибки в `migration.accounts` (без секретов).
- `retry` повторяет только failed-аккаунты; остальные не затрагиваются.
- `root_mismatch` означает, что исходный ключ в копии отличается от
  зафиксированного — миграция этого аккаунта блокируется (fail closed),
  данные не повреждаются.

### Аккаунт с RSA-2048 (rotation, реализовано 17.11.2026)
- `audit` показывает `rotation_required`; `prepare` импортирует аккаунт в
  статусе `rotation_required` и переносит недошедшую очередь (ciphertext
  старому ключу) в `legacyInbox`.
- На устройстве (Android v2, экран «Устройства») пользователь явно запускает
  «Сменить ключ и зарегистрировать»: генерируется НОВЫЙ RSA-4096, старый ключ
  подписывает аттестацию, связывающую account, fingerprint старого корня,
  новый SPKI и точные digest genesis/manifest. Сервер проверяет подпись
  старым публичным ключом из read-only v1-источника и одноразовый nonce.
- **Это смена криптографической идентичности, не её сохранение.** Аккаунт
  (username), контакты, профиль и локальная история сохраняются; якорь v2 —
  новый ключ. Аттестация публикуется в каталоге: собеседники, помнящие старый
  ключ, могут проверить непрерывность владения. Новые собеседники видят новый
  ключ (TOFU). Если старый ключ был скомпрометирован, аттестация тоже
  скомпрометирована — модель это не скрывает.
- Старый приватный ключ остаётся на устройстве (`legacy_key` в зашифрованном
  SQLCipher-хранилище v2 + исходный secure storage v1 не трогается): им
  расшифровывается локальная история и bridged-ciphertext от v1-собеседников.
- Recovery-пакет нового якоря шифруется отдельной фразой; журнал rotation
  crash-safe (новый якорь сохраняется ДО сети; неверная фраза не повреждает
  состояние; повтор после сбоя перенимает серверный каталог).
- RSA < 2048: не подлежит migration/rotation (`unsupported_key_size`),
  остаётся на v1; при выводе v1 — отдельное решение владельца.
- Ограничения: rotation доступен на Android (старый ключ в secure storage);
  web/PWA legacy-мост и rotation пока не реализованы (ZCODE-направление).
  `read`-статус bridged v1→v2 сообщений не транслируется (только delivered).

## 4. Контроль целостности

- `verify` сверяет root каждого аккаунта с read-only источником, проверяет
  digest очереди, отсутствие дубликатов, полноту цепочек каталогов
  (verifyHistory при загрузке snapshot) и согласованность аудит-журнала.
- `status` показывает per-account: статус, попытки, последняя ошибка, revision,
  число устройств, pending/imported очередь, привязку Google.
- Перед каждым prepare обёртка `migration-run.sh` делает проверяемые бэкапы
  обоих хранилищ; `backup-verify.sh` подтверждает читаемость и состав.

## 5. Аудит без раскрытия данных

В отчётах и журнале: имена аккаунтов, счётчики, статусы, коды ошибок,
fingerprint публичного ключа. Никогда: приватные ключи, токены, фразы,
plaintext сообщений, содержимое аватаров. Caddy-логи staging дополнительно
вырезают Authorization/Cookie/X-Session-Token/X-Username.
