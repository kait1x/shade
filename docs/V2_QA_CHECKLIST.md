# P4: QA-программа перехода v2 (чек-листы и критерии)

Все прогоны до 23.11 — ТОЛЬКО локально/на изолированных фикстурах.
Физические устройства — после защиты и отдельного «го» на деплой v2-prod.
Реальные данные тестеров (Даша и др.) не трогаем: recovery/enrollment-учения
только на синтетических тестовых аккаунтах.

## 1. Browser-QA (server/tools/alpha-browser-qa.mjs, Edge + WebKit, normal+hostile)
Локальный HTTPS-фикстура-сервер, два независимых профиля. Сценарии:
1. Регистрация web-first + recovery-пакет скачан; ключи переживают reload.
2. Новый разговор по никнейму (TOFU): чат открыт без диалога отпечатка;
   бейдж «Ключ не сверен»; ручная сверка снимает бейдж; подмена genesis блокирует.
3. E2EE roundtrip текст+медиа; read-ACK; typing/presence; offline-очередь →
   retry тем же ciphertext/id без дублей (hostile-blob режим для Android-класса).
4. Pairing: challenge-код → offer → approve → confirmation → второе устройство
   в ростере; сообщение fanout на оба; отзыв устройства; expired/replay offer.
5. Recovery: file input пакета + фраза → новый vault → ростер заменён →
   плашка «старая переписка недоступна»; неверная фраза/чужой пакет/429 честно.
6. Enrollment-миграция (PWA-сторона моста): v1-аккаунт → legacy-enrollment →
   inbox моста дренируется; счётчики до/после совпадают.
7. history.transfer: доверенное устройство → пакеты → новое устройство fetch по
   курсору → ack → staging пуст; повтор без дублей.
Критерий: PASS оба движка × normal+hostile; любой FAIL = NO-GO до фикса.

## 2. Физический QA (A31 владельца + iPhone тестера), после деплоя v2-prod по «го»
Сборка нативного v2: `flutter build apk --release --target lib/main_native_v2.dart
--dart-define-from-file=config/<v2-prod>.json` + key.properties (ключ у владельца).
Чек-лист (каждый пункт: ожидание / факт / подпись):
1. Установка v2-APK рядом с v1 (разные applicationId до cutover) — v1 не ломается.
2. Регистрация нового аккаунта в нативе v2; recovery-пакет сохранён вне устройства.
3. Enrollment СУЩЕСТВУЮЩЕГО тестового v1-аккаунта: личность тем же RSA-ключом
   (отпечаток device-ключа совпадает с v1), история импортирована локально
   (счётчик записей до/после), v1-хранилище неизменно.
4. E2EE диалог натив-v2 ↔ PWA: текст, фото, прочитано, typing, в сети.
5. Offline: авиарежим → история читается, отправка queued → сеть → delivered
   без дублей; повторный запуск приложения сохраняет очередь.
6. Pairing A31 ↔ iPhone (или второй профиль): код/offer/approve; fanout; отзыв.
7. Recovery-учение на ТЕСТОВОМ аккаунте: удалить локальный vault (не passkey
   тестера!) → восстановление пакетом → новый ростер → старая история честно
   недоступна; 429 после 5 попыток/час.
8. Push: Firebase service-account key на сервере + google-services.json →
   уведомление при закрытом приложении (натив) и Web Push (PWA).
9. Медиа: фото/стикеры рендерятся, размер-лимиты честно.
10. Производительность/UX: клавиатура не перекрывает composer, скролл истории,
    тёмная тема, увеличенный шрифт, 320 px.
Критерий: все пункты подписаны владельцем/тестером; любой провал = NO-GO.

## 3. Restore/rollback (P5, изолированно, по «го»)
1. Копия staging-данных в изолированный каталог + копия storage secret (владелец,
   вне Git/чата) → boot восстановленного инстанса → health + directory + счётчики
   аккаунтов/очередей совпадают с оригиналом; sha256 архива зафиксирован.
2. Репетиция rollback на staging: симлинк назад + restart + Caddy reload из
   бэкапа → smoke обоих origins → UPDATE_DONE-эквивалент; время отката записано.
3. Внешняя копия бэкапа у владельца подтверждена (без секретов в Git/чате).

## 4. Сводка GO/NO-GO
GO = §1 PASS + §2 подписан + §3 PASS + RC (SHA/manifest/логи) + защита проведена +
отдельные «го» на каждый prod-шаг. NO-GO триггеры — план §5.
