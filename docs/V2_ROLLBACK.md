# Shade v2: откат (rollback)

Откат бывает двух видов; их нельзя путать. Ни один из них не изменяет и не
удаляет v1-данные: миграция аддитивна, `users.json`/`messaging.json`/
`stickers.json`/ключи/токены v1 остаются нетронутыми.

## 1. Что можно откатить безопасно

### Guard-off (возврат переведённых аккаунтов на v1)
Удаление/отключение guard-файла (`SHADE_V2_GUARD_FILE`) возвращает аккаунтам
доступ к v1-маршрутам в течение ~1 с (mtime-кэш).
```bash
bash deploy/staging/rollback-v2.sh guard-off <guard-file>
```
**Условие безопасности**: с момента enrollment не было обмена сообщениями по
v2. Если v2-сообщения уже ходили, возврат на v1 означает:
- v2-очередь недоступна v1-клиенту → недоставленные v2-сообщения не дойдут,
  пока аккаунт снова не включён в v2 (ciphertext сохраняется в snapshot);
- новые v1-сообщения снова пойдут через v1-очередь.
Поэтому guard-off после начала v2-переписки — **ограниченный** откат: он не
теряет уже сохранённое, но создаёт «разрыв» доставки между версиями. Решение
принимает владелец; предпочтительно не откатывать enrolled-аккаунты, а чинить
v2 вперёд.

### Rollback prepared-аккаунтов (до enrollment)
Аккаунт без genesis/каталога можно удалить из v2-реестра:
```bash
node server/tools/migrate-v1-to-v2.mjs rollback --target <v2-dir> --accounts a,b --confirm
```
CLI сначала сохраняет проверяемый бэкап snapshot в
`<v2-dir>/rollback-backups/<stamp>/device-v2.enc`, затем удаляет только
prepared-записи (аккаунт, migration-журнал, legacyInbox, stickers-копию).
Enrolled-аккаунты откатывать этим способом **запрещено**
(`rollback_refused_enrolled`) — удаление живого каталога осиротит доверие
устройств и очереди.

## 2. Откат enrolled без потери новых сообщений (replay-restore)

С 17.11.2026 доступен **lossless replay**: восстановление старого бэкапа с
переносом более нового живого состояния. Движок `server/multidevice/rollback-journal.mjs`
сливает снапшоты по event-монотонной модели:

- очереди: живые записи приоритетны; записи из бэкапа восстанавливаются,
  только если живые реестры не доказывают пост-бэкап ACK/retract/revocation
  (удалённый ciphertext никогда не «воскресает»);
- receipts/delivery/retractions: объединение с приоритетом живого состояния
  (конфликт digest — fail closed);
- каталоги устройств: более новая цепочка ревизий сохраняется, только если
  она продолжает цепочку бэкапа точным подписанным префиксом; после слияния
  вся цепочка genesis→ревизии криптографически перепроверяется реестром;
- legacyInbox/migration: дедуп-объединение, ACK-тумбстоуны сохраняются.

Процедура (сервис `shade-alpha` остановлен):
```bash
systemctl stop shade-alpha
node server/tools/migrate-v1-to-v2.mjs replay-restore \
  --target <v2-dir> --backup <старый device-v2.enc или его каталог> --confirm
systemctl start shade-alpha
node server/tools/migrate-v1-to-v2.mjs verify --source <v1-dir> --target <v2-dir>
```
CLI сначала делает проверяемый бэкап текущего живого снапшота в
`<v2-dir>/rollback-backups/<stamp>-pre-replay/`, затем атомарно сохраняет
результат слияния. Любой конфликт (расхождение цепочек, подмена root/genesis,
конфликт digest) abort-ит операцию **без изменения target**.

Дополнительно: `ALPHA_CHECKPOINT_DIR` (+ `ALPHA_CHECKPOINT_KEEP`)
включает durable скользящие checkpoints каждого сохранённого снапшота (по умолчанию 20) —
точки восстановления для forensic/rollback. Команда `checkpoint --target
<v2-dir> --out <dir>` делает разовый проверяемый бэкап.

Доказано интеграционными тестами `server/test/rollback-journal.test.mjs`
(5/5 PASS, 17.11.2026): пост-бэкап сообщения/ACK/read/retract/новое устройство
переживают restore; отзыв устройства не воскрешается; расхождение цепочек
fail closed без изменения target; checkpoints ограничены и расшифровываются.

### Ограничения (честно)

- Если живой снапшот **нечитаем/повреждён**, replay невозможен (источник
  событий утрачен): остаётся только snapshot-restore из бэкапа с потерей
  пост-бэкап очередей с relay (локальные копии на устройствах сохраняются).
  Скользящие checkpoints уменьшают окно потери до последнего checkpoint.
- Replay не «отменяет» намеренные действия после бэкапа (ACK/retract
  применяются поверх). Если после бэкапа был намеренный rollback prepared-
  аккаунта, replay восстановит его запись — повторите rollback после replay.
- Устройства, добавленные после точки бэкапа, восстанавливаются вместе с
  подписанными ревизиями; lease мог истечь — потребуется продление.

### Прямой snapshot-restore (только если replay невозможен)

Только осознанно, с разрешения владельца, при остановленном `shade-alpha`:
```bash
systemctl stop shade-alpha
bash deploy/staging/rollback-v2.sh snapshot-restore <backup-device-v2.enc> <v2-dir>
systemctl start shade-alpha
node server/tools/migrate-v1-to-v2.mjs verify --source <v1-dir> --target <v2-dir>
```
Последствия:
- v2-сообщения, поставленные в очередь **после** точки бэкапа, теряются с
  relay. Локальные копии на устройствах (SQLCipher) сохраняются — история на
  устройствах не исчезает.
- Устройства, добавленные после точки бэкапа, теряют членство; потребуется
  повторный pairing/recovery.
- Genesis неизменяем: восстановленный snapshot содержит тот же genesis, что и
  до бэкапа, поэтому клиенты с сохранённым локальным состоянием могут
  продолжить (lease мог истечь — потребуется продление).

## 3. Откат кода v2 (без данных)

Как и v1 (`deploy/vps/deploy.sh`): переключить symlink `current` на предыдущий
релиз и рестартовать службу. **Не подменять текущие данные старой базой** —
это потеряет новые сообщения. Данные и код откатываются раздельно.

## 4. Что откатить НЕЛЬЗЯ

- Изменить genesis / заменить якорь аккаунта (неизменяемость — основа доверия).
- «Вернуть» приватные ключи, утраченные устройством (сервер их не хранит).
- Откатить уже расшифрованную/удалённую локальную историю.
- Автоматически откатывать production без контрольных точек и разрешения.

## 5. Контрольные точки перед любым откатом

1. `status`/`verify` зафиксированы (счётчики до/после).
2. Бэкап v2-snapshot и v1-данных сделан и проверен (`backup-verify.sh`).
3. Определено, были ли v2-сообщения после точки отката (риск разрыва доставки).
4. Владелец подтвердил вид отката и его последствия.
5. После отката — повторный `verify` и health-check; мониторинг очередей.
