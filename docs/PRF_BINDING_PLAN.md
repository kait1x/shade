# PRF-привязка устройства — технический план и модель восстановления

Статус: **на согласование** (п. 6 инструкции). Реализовано в ветке
`zcode/pwa-onboarding-ui`, криптографическая схема НЕ изменена.

## 1. Принцип (п. 1–2 требований)

- **PRF — опциональный способ разблокировки уже защищённого vault, не механизм
  recovery и не единственный фактор.** Vault шифруется ровно как раньше:
  PBKDF2-SHA256 (600 000 итераций) → AES-256-GCM, AAD связывает аккаунт, id и
  публичные ключи (`device_crypto.mjs`, строки не тронуты). PRF лишь поставляет
  **вход** этого KDF — machine-generated строку 43 символа (base64url от 32 байт
  PRF-вывода), вместо придуманной пользователем фразы.
- **Recovery-пакет сохранён полностью независимым:** отдельный RSA-ключ,
  шифрование отдельной (теперь автогенерируемой) фразой, загрузка как файл вне
  устройства. Пакет не содержит ключей устройства и не зависит от passkey,
  iCloud или браузера (тест: `device-binding.test.mjs`, фактор-независимость —
  PRF-фраза не открывает recovery-пакет).
- Утрата passkey/iCloud/устройства при целой IndexedDB = невозможность открыть
  ЛОКАЛЬНЫЙ vault — идентичность восстанавливается recovery-пакетом
  (`unlockRecoveryBackup` → манифест с `signer:'recovery'`; серверная часть —
  в `docs/DEVICE_LINKING_UX.md` §3). Честная копия в UI: при ошибке PRF-разблокировки
  пользователь видит объяснение, а не бесконечный spinner.

## 2. Проверенная поддержка PRF (п. 3)

| Платформа | PRF с платформенным аутентификатором | Источник |
|---|---|---|
| Safari 18+ / iOS 18+, macOS 15+ | да (iCloud Keychain) | WebKit release notes, Yubico guide |
| Chrome/Edge 118+ (Win Hello/Touch ID) | да, с оговоркой ниже | MDN, Bitwarden |
| Firefox | нет → fallback | Mozilla bug tracker |

**Инцидент 18.11.2026 (исправлен):** в первой реализации `prf.eval` передавался
как сырой BufferSource. По спеке WebAuthn L3 `eval` — `AuthenticationExtensions
PRFValues` `{first: BufferSource}`, и Chromium падал на обязательном члене
`first` до всякого запроса к аутентификатору: «Failed to execute 'get' ...
Failed to read the 'first' property ... Required member is undefined». Формат
исправлен (`eval: { first: salt }`), байты salt не менялись — ранее установленных
PRF-vault'ов быть не могло (setup никогда не завершался), миграция не требуется.
Регрессии: mock-тесты `device-binding.test.mjs` (формат `{first}`, отсутствие
члена `first` → честный `prf_unavailable`; детерминизм setup→reopen→unlock) и
браузерный пин `server/tools/prf-browser-check.mjs` (реальный Chromium WebAuthn,
виртуальный аутентификатор). Дополнительно: `user.id` passkey теперь детерминирован
по аккаунту (ретрай setup не создаёт orphan-passkey), при `prf_unavailable` на
setup включается авто-переход на фразу устройства, при недоступности PRF на
разблокировке — честное указание на recovery-пакет; ключи и хранилище при любых
ошибках PRF не затрагиваются.


- Проверка на устройстве: `platformAuthenticatorAvailable()` =
  `isUserVerifyingPlatformAuthenticatorAvailable()` + secure context; повторная
  проверка при каждом запуске онбординга — устаревший браузер не получит PRF-путь.
- **iPhone standalone PWA:** WebAuthn в установленном PWA доступен с iOS 16.4;
  PRF-вывод с платформенным аутентификатором — iOS 18+. На iOS ≤17 и в
  не-PRF-браузерах автоматически используется fallback.
- **Fallback не ослабляет шифрование:** это одна придуманная фраза устройства
  (≥16 симв.) через тот же KDF/AES/AAD. Строго паритет с текущим прод-поведением
  (минус одна recovery-фраза — она генерируется, не придумывается: 8 слов EFF,
  ~103 бита против типичных ~40–60 бит пользовательских фраз).
- Headless-движки QA не имеют аутентификатора → весь browser QA выполняет
  fallback-путь; PRF-путь помечен как требующий ручной проверки на реальном
  iPhone (см. §5).

## 3. Формат vault — обратная совместимость и миграция (п. 4)

- Ciphertext, salt, iv, AAD, KDF-параметры — **байт-в-байт без изменений**.
- Единственное расширение: опциональное несекретное поле `binding`
  `{method:'prf', credentialId, salt}` в записи IndexedDB. `saveVault` валидирует
  форму; старые клиенты игнорируют лишнее поле (`unlockVault` читает только
  известные поля). Смена/подмена `binding` не помогает атакующему (фраза нигде
  не хранится, ciphertext не пересоздаётся) — только локальный DoS-эффект,
  эквивалентный удалению vault.
- Тесты `server/test/device-binding.test.mjs` (Node + fake-indexeddb + WebCrypto):
  1. PRF-образная фраза (43 симв.) через полный create/unlock;
  2. неверная фраза не расшифровывает (OperationError);
  3. `binding`-метаданные не трогают ciphertext, vault открывается при наличии поля;
  4. легаси-запись (точный старый набор полей) сохраняется и разблокируется;
  5. автогенерированная recovery-фраза: 8 слов, ≥24 симв., открывает пакет,
     PRF-фраза пакет НЕ открывает.
- Миграция данных НЕ требуется: старые vault'ы продолжают открываться фразой
  (UI определяет метод по `binding`, иначе — поле фразы). Апгрейд legacy→PRF
  на существующем vault сознательно НЕ делается (это была бы ротация KDF-входа —
  отдельная согласованная задача).

## 4. Разграничение синхронизаций (п. 5)

- **Passkey (iCloud Keychain):** синхронизирует ТОЛЬКО материал для вывода
  локальной фразы этого браузера/происхождения. Не содержит и не передаёт:
  ключи E2EE, историю, контакты, recovery-ключ.
- **Синхронизация Shade:** устройства, история и ключи распространяются
  исключительно через device-v2 манифесты и зашифрованные relay-очереди;
  passkey на это не влияет и устройством Shade не является.
- В UI формулировки разделены: PRF — «защита этого устройства», recovery-пакет —
  «восстановление аккаунта», синхронизация переписки — E2EE-канал.

## 5. Что требует ручной проверки (не покрыто автоматикой)

1. Реальный iPhone (iOS 18+, установленная PWA): создание passkey, второй
   биометрический промпт при регистрации, разблокировка после перезапуска PWA,
   поведение после удаления passkey в настройках.
2. iCloud-синхронизация passkey между двумя устройствами Apple (PRF-вывод
   стабилен; платформенный путь, гибридный QR не используется).
3. Chrome/Edge desktop c Windows Hello.

## 6. Открытые вопросы для согласования (Qwen/владелец)

1. Политика `userVerification: 'required'` при каждом разблоке — сохранена как
   безопасный дефолт; рассмотреть `'preferred'` только после UX-обсуждения.
2. Восстановление локального vault после утраты passkey — принять текущее
   сообщение об ошибке (рулится через recovery-пакет) или добавить явную
   кнопку «Удалить недоступные ключи этого браузера».
3. Серверный pre-check занятости никнейма (сейчас коллизия выявляется только
   на `register`) — фича-запрос в `docs/DEVICE_LINKING_UX.md`.
