# D1: когортная миграция целыми диалогами (утверждено владельцем 20.11)

Единица миграции — **диалог (пара аккаунтов) с учётом ВСЕХ устройств обоих
участников**. Закрытая бета полностью на v2; публичный переход — когортами.
Инварианты владельца: без потерь/дублей/неверного порядка; без переключения до
готовности обоих и подтверждения переноса очередей; без незаметной отправки в
несовместимое окружение; явное состояние ожидания; безопасный rollback;
offline и повторная доставка проверены отдельно.

## 1. Состояния диалога (серверный journal, per-dialog)
`v1_active → migration_pending → transferring → v2_active`, плюс `abort → v1_active`
(до cutover) и `rollback → v1_active` (после cutover, grace-окно).
- `migration_pending`: оба аккаунта enrolled в v2; клиент каждого участника
  подтвердил readiness ВСЕХ своих устройств (device-proof ack по каталогу);
  баннер «Ожидание собеседника/устройств», отправка в диалог разрешена только
  в текущем окружении (v1), новые v2-сообщения в диалог не принимаются.
- `transferring`: перенос очередей v1→v2 для диалога (мост syncInbox scoped by
  dialog) + подтверждение счётчиков и last-seq с обеих сторон; клиентские
  outbox пусты (ack); отправка_HOLD: клиент видит «Диалог переносится…»,
  сообщения встают в локальную очередь и НЕ уходят в несовместимое окружение.
- `v2_active`: атомарный flip routing-флага диалога только после gate-проверок
  (§2); обе стороны получают событие смены окружения; v1-очереди диалога
  дренированы и помечены transferred (не удалены до cutoff+grace).
- `rollback`: routing назад в v1 + reverse-journal replay v2-origine сообщений
  в v1-очереди (§4); состояние и journal сохраняются для аудита.

## 2. Gate переключения (все условия обязательны, fail-closed)
1. Оба аккаунта enrolled; каталоги устройств проверены клиентами (checkpoint).
2. Readiness-ack от ВСЕХ устройств обоих участников (устройство offline → ждём,
   без таймаут-форса; явное состояние ожидания в UI).
3. v1-очереди диалога: pending=0, transferred-счётчик совпадает с journal.
4. Клиентские outbox диалога пусты (подписанный ack), in-flight send нет.
5. Journal диалога непрерывен (seq монотонен, previous-hash цепочка).
Невыполнение любого → остаёмся в transferring/pending, честный текст причины.

## 3. Порядок, дубли, offline
- Per-dialog seq присваивается origin-мостом при постановке в journal; доставка
  клиенту сортируется по seq; дедуп по message-id на обеих сторонах (повтор с
  тем же id и digest = ретрай, конфликт id/digest = отказ).
- Offline участника: journal хранит пакеты до ack; повторная доставка тем же
  ciphertext/id (идемпотентность); после reconnect клиент добирает по курсору.
- Повторный перенос (краш между transfer и flip): journal курсор + идемпотентные
  пакеты; flip атомарен (CAS по revision journal).

## 4. Rollback и криптографическая совместимость
- v2-envelope для legacy-устройства (ключ = v1 RSA) структурно совместим с
  decryptData нативного v1 (проверено interop-тестом: native расшифровывает
  web-сообщение). Reverse-journal replay кладёт v2-ciphertext в v1-очередь
  legacy-устройства как есть → v1-клиент читает историю периода v2.
- Ограничение (честно, в UI и доках): устройства, добавленные ПОСЛЕ миграции
  (новые ключи), v1-клиентом не читаются; rollback восстанавливает сервис на
  legacy-устройствах участников. Новые сообщения после rollback идут в v1.
- Grace-окно rollback: 14 дней после cutover диалога; v1 data не prune-ится.

## 5. Запрет незаметной несовместимой отправки
Клиент перед send проверяет routing-состояние диалога (проекция + подписанный
fetch); при рассинхроне (клиент v1, диалог v2_active или наоборот) — явная
ошибка «Диалог перенесён в Shade v2, обновите приложение» / «Ожидание
миграции», сообщение HOLD в outbox, тихой отправки нет.

## 6. Тесты (обязательны для GO)
server/test/cohort-migration.test.mjs + client interop:
happy path (оба ready → flip → поток v2); один offline → pending без потерь;
replay дублей transfer → дедуп; перемешанная доставка → порядок по seq;
краш между transfer и flip → resume без дублей; abort до flip → v1 нетронут;
rollback после flip → reverse replay читается нативным CryptoService (interop);
send при рассинхроне окружений → HOLD + честная ошибка.

## 7. Реализация (порядок)
1. Сервер: dialog-routing journal + gate + scoped transfer + reverse replay
   (migration.mjs расширение, аддитивно; v1 server.js получает routing-флаг
   через мост, БЕЗ изменения v1 формата сообщений).
2. Клиенты: проекция состояния диалога + HOLD-логика + баннеры (PWA и натив v2).
3. Тесты §6 + browser-QA сценарий миграции на двух профилях.
