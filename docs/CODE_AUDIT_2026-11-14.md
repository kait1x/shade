## Приоритет P1 — исправить до публичного запуска

### A01. Выход может завершать чужую сессию, а обычный выход клиента ничего не отзывает

`server/server.js:809–818,1397–1433`; `client/lib/core/services/connection_service.dart:612–625`.

Middleware проверяет `x-username`, но обработчик выбирает пользователя из `req.body.username`. С токеном Alice и заголовком Alice можно передать Bob в body: сервер возвращает 200 и токен Bob перестаёт работать. Также клиент посылает только заголовки без body с username: сервер отвечает 200, но токен Alice остаётся действительным.

Воспроизведены оба варианта. Исправить: закрепить проверенную личность в `req.auth`, работать только с ней, отозвать связанную grace-сессию и текущий сокет. Не удалять недоставленные сообщения как побочный эффект обычного logout.

### A02. `/refresh` взаимно блокирует сам себя

`server/server.js:715,772–774,1436–1458`.

Обработчик захватывает `refreshTokenMutex` и вызывает `validateRefreshToken`, который снова ожидает тот же нерекурсивный mutex. Позже `generateRefreshToken` также захватывает его. Запрос с произвольным непустым refresh token зависает, удерживая блокировку для следующих запросов этого механизма. Основной обмен сообщениями при этом не объявляется зависшим.

Воспроизведён таймаут. Исправить: одна блокировка вокруг всей операции проверки и ротации; внутренние функции не должны захватывать её повторно. Проверить ошибочные токены и параллельные запросы.

### A03. Удаление чата не отменяет отправку его офлайн-сообщений

`client/lib/core/database/database_service.dart:450–454`; `connection_service.dart:578–605`.

Удаляются `messages` и `conversations`, но остаются строки `outbox`. При восстановлении сети `flushOutbox()` отправит текст, который пользователь уже удалил вместе с чатом. SQLite-проба подтверждает оставшийся payload после удаления.

Исправить атомарным удалением связанной очереди в одной транзакции; отдельно определить поведение уже выполняющейся отправки.

### A04. Сервер разрешает отправлять сообщения в группу постороннему пользователю

`server/server.js:1604–1640,1850–1882`.

`groupMessage` проверяет авторизацию и существование группы, но не `group.members.has(from)`. Авторизованный Carol, отсутствующий в группе Alice/Bob, смог отправить им `groupMessage`. Хотя группового интерфейса сейчас нет, API доступно.

Исправить проверкой членства и входных данных либо отключить незавершённые групповые маршруты. GET `/group/:id` также раскрывает состав без авторизации. Не выдавать этот модуль за готовые группы.

### A05. Admin logout не отзывает серверную сессию

`server/server.js:832–872,1158–1186`.

Map хранит raw token, cookie содержит `token.signature`. `adminSessions.delete(sessionCookie)` удаляет неправильный ключ. После `/admin/logout` сохранённая старая cookie по-прежнему даёт 200 от защищённого `/api/stats`.

Воспроизведено без вывода cookie или пароля. Исправить проверкой/разбором cookie и удалением raw token, затем тестом повторного использования cookie после выхода.

## Приоритет P2 — функциональная надёжность и безопасность

### A06. Push-путь несовместим между клиентом и сервером

`client/lib/core/services/notification_service.dart:80–110,123–178,236–270`; `auth_notifier.dart:100–152,188`; `server/server.js:1462–1510,1573–1595`.

Клиент отправляет RSA-зашифрованный FCM token. Сервер сохраняет его и передаёт Firebase как token без расшифровки. Это не исходный регистрационный токен устройства. Дополнительно:

- После нового Google-входа `init()` вызывается, а `registerToken()` — нет; регистрация есть в восстановлении профиля.
- При refresh FCM token обновляется только локальная переменная.
- Сервер отправляет data с `from`, а клиент при нажатии ждёт `conversationId`.
- Background handler объявлен, но `FirebaseMessaging.onBackgroundMessage` нигде не зарегистрирован; серверный silent push сам по себе не создаёт нужное уведомление Android.
- Подписки FCM не отменяются в dispose, unregister не передаёт сессию и сравнивает object с token string на сервере.

Подтверждено по исходникам, реальный Firebase push не проверялся. Нужен единый протокол, регистрация после входа/обновления, фоновые обработчики и тест на двух телефонах.

### A07. Дедупликация на клиенте имеет неправильную область уникальности

`server/direct-messaging.js:14,33–52`; `client/lib/core/database/database_service.dart:73,333,475–481`; `connection_service.dart:675–678`.

Сервер различает сообщения по `(from,id)`, клиент — только по `network_id`. Сообщение Carol с ID уже существующего сообщения Bob пропускается, хотя сервер считает их разными. SQLite-проба воспроизводит потерю второй записи. Для случайных 192-битных ID совпадение крайне маловероятно; проблема существенна при намеренно выбранных ID.

Исправить общей моделью идентичности, включая отправителя, миграцией индекса и адресацией квитанций/удалений.

### A08. Дедупликация сервера пропадает после доставки и рестарта

`server/server.js:523`; `server/direct-messaging.js:32–56,94–99`.

`directReceipts` существует только в RAM. После delivered сообщение удаляется из офлайн-очереди. После рестарта сервер не знает этот ID и принимает старый payload повторно. Проба реально получила повторный envelope. Это не означает, что обычный клиент обязательно покажет вторую копию: текущая SQLite-дедупликация может её скрыть; гарантия серверной идемпотентности всё равно нарушена.

Исправить сохранением receipt/tombstone с явно заданным TTL и правилами конфликтов ID.

### A09. Доставка и прочтение не догоняют отключённого отправителя

`server/direct-messaging.js:10–13,73–99`; `connection_service.dart:578–605`.

После ACK отправитель удаляет свою outbox-запись. Если позже получатель подтвердит доставку/прочтение, пока отправитель офлайн, `emitTo` ничего ему не отправит и не создаст очередь событий. После reconnect replay статуса отсутствует. Проба подтвердила отсутствие `messageStatus`. У отправителя сообщение может навсегда остаться «отправлено».

Нужен серверный журнал статусов и согласование после reconnect; хранить его вместе с устойчивой дедупликацией A08.

### A10. Подтверждение доверия к ключу сервера фактически не включено в основной поток

`client/lib/core/services/connection_service.dart:195–246,249–255,390–415`; `crypto_service.dart:275–305,323–440`.

`verifyPublicKeySignature` проверяет математическую подпись и возвращает true без вызова проверки сохранённого fingerprint. UI не вызывает `checkServerKeyConfirmation`. Отдельный `SERVER_PUBLIC_KEY_FINGERPRINT` в ConnectionService работает, если явно задан. `SHADED_PIN_SHA256` используется одновременно как base64 digest TLS-сертификата и как colon-hex fingerprint PEM-ключа в другом коде — эти значения различаются.

Это не отключает обычную проверку TLS CA: она сохраняется. Но заявленная дополнительная TOFU-защита отсутствует без отдельного build pin. Разделить настройки TLS pin и server-key pin, включить подтверждение/блокировку и проверить смену ключа. Подпись сервера сейчас связывает только public key, не username; независимой проверки ключа собеседника нет.

### A11. Прочтение последней страницы помечает прочитанной всю историю

`client/lib/features/chats/presentation/screens/chat_screen.dart:232–267,288–325`; `database_service.dart:521–529`.

UI загружает 20 сообщений и посылает read для их ID, затем `markMessagesAsRead(conversationId)` меняет все непрочитанные строки. Для 25 сообщений пять старых также становятся локально прочитанными, хотя read по их ID не посылался; при догрузке отдельной отправки read нет. SQLite-проба воспроизводит это состояние.

Исправить обновлением конкретных ID и определением момента реального просмотра, включая загрузку старых страниц.

### A12. Уведомление внутри приложения ищет ScaffoldMessenger выше MaterialApp

`client/lib/main.dart:66–75`; `client/lib/core/widgets/notification_overlay.dart:36–37`.

NotificationOverlay оборачивает MaterialApp, поэтому его context не является потомком созданного MaterialApp ScaffoldMessenger. `maybeOf(context)` возвращает null, обработчик молча прекращается. Исправить размещением через MaterialApp builder либо общим scaffoldMessengerKey. Подтверждено структурой виджетов, отдельная визуальная end-to-end проверка не выполнялась.

## Остальные замечания и границы проверки

- Анализатор сообщает о `AESFastEngine` с предупреждением о side-channel issues (`crypto_service.dart:143,195`). Заменить поддерживаемой реализацией без изменения формата ciphertext и проверить совместимость; успешный round trip не доказывает отсутствие побочных каналов.
- В WebSocket connection limiter счётчик увеличивается до ранних return по reconnect/throttle, а disconnect cleanup ставится позже (`server.js:1674–1699`). Возможна утечка счётчика и отказ новым соединениям с того же IP. «10/sec» считается по миллисекундному Date.now, а не секундному окну (`1654–1663`). Проверено статически, нагрузочный прогон не выполнялся.
- Release Android сейчас подписывается debug key (`client/android/app/build.gradle.kts:40`); новый Google OAuth Client ID в проверочный APK не передавался. Нужен отдельный release signing/OAuth-процесс. API 23 не поддерживается текущей выбранной сборочной средой (min API 24).
- Compose принудительно задаёт development, не передаёт GOOGLE_WEB_CLIENT_ID и по умолчанию задаёт слишком короткий DASHBOARD_PASS, с которым сервер сам откажется стартовать. Dockerfile не устанавливает openssl, хотя автогенерация сертификата пытается его вызвать. Сборка/старт Docker здесь не проверялись; использовать подготовленные сертификаты и явные настройки.
- `server/.env` присутствует в Git-истории (`225ff6a`, `1d6e55a`), хотя в рабочем индексе уже удалён. Значения не читались и не приводятся. Удаление из последнего коммита не удаляет историю; если там были настоящие секреты, их необходимо заменить. История автоматически не переписывалась.
- iOS проверен только статически: в `AppDelegate.swift` есть `self?.` вне weak-self closure (неопциональный self), подозрительные lifecycle/blur вызовы и отсутствие подтверждённой сборки. Уведомление о снятом скриншоте происходит после снимка и не означает запрет скриншотов. macOS/Xcode недоступны; iOS не объявляется работающим.
- Windows/macOS/Linux не проверялись. Desktop ветка базы использует мобильный SQLCipher plugin; SQLite-пробы применяют специально подставленный FFI factory и не доказывают работоспособность production desktop базы.
- README и KNOWN_ISSUES содержат устаревшие утверждения («всё исправлено», старая палитра, схема входа). Сверить с этим аудитом после исправлений.
- Нет проверки реального Google OAuth, двух физических телефонов, Firebase push, release установки, работы под нагрузкой или длительного background режима. Запуск локальных Socket.IO test-клиентов не выдаётся за такой тест.
