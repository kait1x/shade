# Подключение второго устройства и восстановление — UX-требования для Qwen

Подготовлено в ветке `zcode/pwa-onboarding-ui` (редизайн онбординга Web Alpha).
Протокол E2EE и device-v2 НЕ меняются. Ниже — UX-состояния, копирайт и точечные
серверные требования, которые остаются на стороне Qwen.

## 0. Что уже есть (не проектировать заново)

- `device_binding.mjs`: привязка устройства через WebAuthn PRF (passkey + вывод
  ключа), fallback — фраза устройства. Vault-формат не менялся.
- Авто recovery-фраза (8 слов EFF, ~103 бита) + offline recovery-пакет,
  `unlockRecoveryBackup` / `finalizeRecoveryBackup` / `rebindPendingBackup`.
- `device_crypto.approveDevices(genesis, history, roster, session, checkpoint)` —
  выпуск манифеста с произвольным составом устройств (это и есть approve).
- `pairingProof(vault, session)` — подписанное предложение устройства.
- Сервер: `registry.install(manifest, proofs, genesis)` — generic-вход;
  `verifyHistory` уже принимает манифесты с `signer === 'recovery'` (index > 0),
  т.е. recovery-подписанные манифесты валидируются протоколом.
- Клиент: экран «Нужна привязка устройства» (`linkStep` в alpha-ui.mjs) —
  текущая заглушка; сюда встраивается новый флоу.

## 1. Флоу «второе устройство» (новое устройство → уже подключённое)

Пользовательский путь на новом устройстве:

1. «Продолжить с Google» → OAuth handoff (существующий).
2. `/api/session` возвращает `account`, локальных vault'ов нет →
   вместо сегодняшней заглушки — экран **«Подключить это устройство»**:
   - подзаголовок: «Ключи этого аккаунта живут на уже подключённом устройстве.
     Подтвердите вход там — и они не покинут ваши устройства.»
   - крупный primary-код привязки (6–8 цифр, TTL 5 мин) или QR с
     `{account, newDevice: descriptor + pairingProof, code}`.
3. Экран **«Ожидаем подтверждение»**: прогресс-состояние (spinner + «Откройте
   Shade на подключённом устройстве»), кнопка «Отменить».

На уже подключённом устройстве (push-сигнал или при следующем sync):

4. Диалог **«Добавить устройство?»** (Android AlertDialog-стиль, web: dialog):
   - «@account просит доступ к вашей переписке» + код совпадения,
   - отпечаток нового устройства (fingerprint descriptor'а, моно),
   - кнопки: «Добавить устройство» (primary) / «Отклонить» (outline).
   - Требование безопасности: подтверждение ТОЛЬКО подписью доверенного
     устройства (`approveDevices`), сервер/Google не могут подтвердить.
5. После одобрения новое устройство получает манифест (`install`), создаёт
   локальный vault, показывает **«Синхронизация»**.

Состояния/edge cases: отклонено («Устройство не добавлено» + повтор), истёк
код (перегенерация), оффлайн доверенного устройства (код живёт до 5 мин),
отзыв (existing devices.revoke).

### Серверные требования (Qwen)

- Канал заявок на привязку: `{code → descriptor+proof, TTL ≤5 мин, capacity cap}`
  — по аналогии с OAuth `flows`/`handoffs`, без БД-миграций.
- Способ доставки заявки доверенному устройству: событие socket.io
  (`link.request`) для онлайн + wake-push для офлайн. Текст сообщений не
  передаётся — только сигнал.
- `install` нового устройства на новом девайсе должен работать через
  существующий `POST /api/v2/operation {op:'install'}` при наличии
  валидного device-Proof от НОВОГО устройства (проверить текущее ограничение:
  требует ли proof от уже зарегистрированного устройства).
- Rate limits: создание заявок ≤ 10/мин/сессия; подтверждение ≤ 30/мин.

## 2. Экран синхронизации (новое устройство после approve)

- Карточка «Синхронизация переписки» с прогрессом: количество загруженных
  сообщений/контактов, spinner ShadeLoading-стиля; под ним — «Проверяем ключи
  собеседников» (прогресс по `verifyContact` непроверённых).
- Кнопка «Открыть мессенджер» активна сразу после базового sync (история
  догружается в фоне — существующее поведение `client.sync()`).
- Отмена/закрытие не ломает синхронизацию: фоновые операции идемпотентны
  (existing CAS/`exclusive`).

## 3. Восстановление при потере всех устройств

Пользовательский путь (тот же welcome → Google):

1. «Нужна привязка устройства» → кнопка «Восстановить с recovery-пакетом».
2. Экран **«Восстановление»** (переиспользует onboard-каркас):
   - загрузка recovery-пакета (file input) + поле «Recovery-фраза»,
   - предупреждение: «Пакет вернёт членство в аккаунте с новым ключом
     устройства. Старые устройства, если они найдутся, не получат доступ»,
   - primary «Восстановить» → `unlockRecoveryBackup(backup, phrase, genesis)`
     + подпись нового манифеста recovery-ключом (`signer:'recovery'`),
3. Затем — стандартная регистрация vault'а нового устройства + экран
   синхронизации. Сообщения, отправленные до потери, недоступны (они были
   зашифрованы под старые устройства) — показать честную плашку.

### Серверные требования (Qwen)

- Проверить/допустить `registry.install` манифестов, подписанных
  recovery-ключом: proof-механика для «устройства recovery» (в клиенте
  `unlockRecoveryBackup` возвращает `{account, id:'recovery', signing}` —
  серверный challenge/proof должен принимать signer id `recovery`).
- Лимиты: восстановление ≤ 5/час/аккаунт; каждая попытка логируется метаданными
  (без содержимого).
- Ротация: после recovery следующая выдача каталога обязана содержать только
  новые устройства (старые считаются утраченными) — проверить поведение
  expiresAt/lease.

## 4. Переиспользование UI-компонентов (эта ветка)

- Каркас `onboard()` (brand + medallion + карточка + dots + fineprint),
  `expander()`, `showProgress()`, `input()/submit()`, классы `.btn/.field-*`.
- Стили уже соответствуют Android-теме; новые экраны добавлять через
  `onboard({...})`, не создавая параллельную систему стилей.
- Дизайн-токены: `alpha.css` `:root` переменные.
