# Блокер открытой беты: PRF-vault без рабочего recovery UI

Статус: **зафиксирован как блокер открытой беты** (закрытый staging-тест
допустим с оговорками ниже). Текущий релиз-кандидат (runtime 5783295) НЕ
затрагивается этим документом и не меняется.

## 1. Суть блокера

- Vault, созданный через PRF (`binding.method='prf'`), шифруется фразой,
  машинно-выводимой из passkey (PBKDF2-600k → AES-256-GCM, формат не менялся).
  Пользователь эту фразу не знает и не хранит.
- При утрате passkey (удаление в настройках, сбой iCloud Keychain, потеря
  устройства) локальный vault не открыть: поле фразы при разблокировке
  скрыто (`alpha-ui.mjs unlockStep`), фразового fallback для PRF-vault нет.
- Recovery-пакет (отдельный RSA-ключ + автофраза) криптографически независим
  и валиден, но **пользовательского пути восстановления нет**:
  `unlockRecoveryBackup`/`finalizeRecoveryBackup` существуют как примитивы,
  recovery-экрана в UI нет, серверной recovery-сессии нет.
- Следствие: потеря passkey = потеря локальной идентичности без пути
  восстановления через интерфейс. Для открытой беты это недопустимо.
- Сценарий «все устройства потеряны» усугубляет: pairing требует живого
  доверенного устройства; recovery-пакет остаётся единственным активом.

## 2. Почему минимальное решение требует малой серверной добавки

Протокол УЖЕ принимает recovery-подписанные манифесты: `verifyHistory`
(device-v2.mjs:121) использует `genesis.recoveryKey` как authority при
`signer==='recovery' && index>0`. Но клиент не может построить manifest
revision+1 без текущего каталога: op `directory` требует device-proof
активного устройства ростера, которого при потере всех устройств нет.
Курица-яйцо → нужна короткоживущая recovery-сессия (план
MULTIDEVICE_SYNC_PLAN §5.1), разрешающая ТОЛЬКО `directory` и `install`.

## 3. Минимальное безопасное решение (отдельная согласованная задача)

Сервер (аддитивно, без изменения криптопротокола и форматов):
1. `POST /api/v2/session/recovery`: challenge → подпись recovery-ключом из
   принесённого genesis; сервер сверяет `genesisDigest` с хранимым и
   `genesis.recoveryKey`; сессия `kind:'recovery'`, TTL ≤ 10 мин,
   rate limit ≤ 5/час/аккаунт; разрешённые ops: только `directory`, `install`.
2. `install` принимает manifest с `signer:'recovery'` (verifyHistory уже
   валидирует) + possession proof нового устройства (v1/v2 как сейчас);
   ростер заменяется на новые устройства, старые retire-ятся существующим
   механизмом tombstones.
Клиент (новый экран, переиспользует onboard-каркас):
3. «Восстановить с recovery-пакетом»: file input пакета + поле recovery-фразы
   → `unlockRecoveryBackup` → новый vault (фраза или PRF по выбору) →
   recovery-сессия → `directory` → manifest revision+1 со signer 'recovery'
   (только новое устройство) → `install` → device-session bootstrap →
   обычный sync. Честная плашка: старая история недоступна (шифровалась под
   утраченные ключи).
Тесты: неверная фраза, чужой/подменённый genesis, replay сессии, запрет
прочих ops для recovery-сессии, rate limit, retire старых устройств,
полный flow против реального registry; browser QA сценарий восстановления.
Совместимость: аддитивный маршрут + существующие примитивы; C1–C7, install
для обычных сессий, vault-форматы не меняются; старые клиенты не затрагиваются.

## 4. Немедленная митигация без изменения релиза (UX-only, отдельная ветка)

- На экране PRF-создания: явное предупреждение «Без passkey локальный vault
  не открыть; восстановление через интерфейс появится позже» + обязательный
  чекбокс понимания + заметная кнопка фразового пути.
- На ошибке PRF-разблокировки: честный текст с объяснением (частично уже есть
  через bindingErrorText) и указанием, что recovery-пакет сохранён вне
  устройства; без dead-кнопок.
- Для закрытого теста: рекомендовать фразовый путь на тестовых устройствах
  либо PRF с сохранённым passkey; «удалил passkey» — ожидаемая блокировка.

## 5. Решение владельца

Открытая бета блокируется до реализации §3 (или явного принятия риска с
фразовым путём по умолчанию). Закрытый staging-тест релиза 5783295/6e22f46
разрешён с оговорками §4. Реализация §3 — отдельная ветка и отдельное
согласование; в текущий релиз не входит.
